# ai-flow

**ai-flow** — это готовый «рабочий процесс» (workflow) для разработки проектов с помощью ИИ-агентов.
Он превращает свободное «сделай мне фичу» в предсказуемый конвейер:

> **идея → PRD → спецификация → задачи → автоматическое выполнение агентом → самоподдержка знаний и документации**

Вся инфраструктура лежит в одном каталоге — `ai-flow/`. В корне проекта остаётся только то, что
ИИ-инструменты находят автоматически: `README.md`, `CLAUDE.md`, `AGENTS.md`, `.claude/`,
`.serena/`.

> **Инструмент по умолчанию — [Claude Code](https://docs.claude.com/claude-code):** субагенты,
> скиллы, хук и MCP настроены именно под него. Работаете в другом агентском CLI (Codex, Cursor,
> Gemini CLI, zcode, …)? Ничего переписывать вручную не нужно — откройте свой инструмент в корне
> проекта и дайте ему промт `ai-flow/docs/prompts/PROMT_TOOL.md`: он сам переложит роли, точки
> входа, хук и MCP на механизмы вашего инструмента. Подробнее —
> [«Другой инструмент, не Claude Code»](#другой-инструмент-не-claude-code).

> Этот README — **учебник**. Если вы впервые видите ИИ-агентов, читайте подряд: разделы
> [«Зачем это нужно»](#зачем-это-нужно), [«Словарь»](#словарь-основные-понятия) и
> [«С чего начать»](#с-чего-начать-пошагово) дадут рабочее понимание за 15 минут. Опытным — сразу к
> [«Командам»](#справочник-команд) и [«Как устроен оркестратор»](#как-устроен-оркестратор-под-капотом).

## Зачем это нужно

Если просто попросить ИИ «напиши мне приложение», он ответит правдоподобным кодом, но:

- **забудет договорённости** — на следующей задаче он не помнит, как вы называете файлы, где лежит
  бизнес-логика, какими командами собирается проект;
- **сам придумает недостающее** — вместо того чтобы спросить, он «догадается», и часто неверно;
- **не оставит следов** — через неделю ни вы, ни другой агент не поймёте, что и зачем было сделано.

ai-flow решает это тремя приёмами:

1. **Разделяй и властвуй.** Большая цель дробится на маленькие самодостаточные *задачи*
   (100–500 строк кода каждая), которые агент делает по одной. Маленькая задача с полным описанием
   выполняется надёжнее, чем большая расплывчатая.
2. **Память вместо угадывания.** Правила проекта, соглашения и паттерны хранятся в файлах
   (`CLAUDE.md` + *память Serena*) и **автоматически подкладываются агенту** в каждую задачу. Он не
   гадает — он читает.
3. **Документация обновляется сама.** После каждой задачи агент дописывает журнал изменений, обновляет
   спецификацию фичи и — если появился переиспользуемый паттерн — сохраняет его в память. Знания не
   теряются.

Итог: вы описываете, что хотите, один раз и на понятном языке, а дальше конвейер выполняет задачи
пачкой, коммитит результат и сам поддерживает документацию в актуальном состоянии.

## Словарь: основные понятия

Прежде чем читать дальше — короткий словарь. Эти слова встречаются во всём README.

| Термин | Что это простыми словами |
|---|---|
| **Агент / кодинг-CLI** | Программа-исполнитель на базе LLM, которая умеет читать и писать файлы в вашем проекте из командной строки. Флоу настроен под [Claude Code](https://docs.claude.com/claude-code); любой другой CLI (Codex, Cursor, Gemini, zcode/GLM) подключается промтом `PROMT_TOOL`. Именно агент пишет код по задаче. |
| **Оркестратор** | Скрипт `ai-flow/run_tasks.py`. Он находит задачи, по очереди запускает агента на каждой, ждёт результат, коммитит и переносит выполненную задачу в архив. «Дирижёр» для агентов. |
| **Спецификация (спека)** | Документ в `ai-flow/docs/specs/`, описывающий, **что** должно быть построено: интерфейсы, структуры данных, критерии приёмки. Read-only контекст для последующих шагов. |
| **Задача (task)** | Один файл-инструкция в `ai-flow/docs/tasks/<фича>/`. Самодостаточное описание одного маленького изменения: что менять, в каких файлах, как проверить готовность. |
| **Фича-папка** | Папка `ai-flow/docs/tasks/<YYYYMMddHHmm_FEATURE>/`, куда сгруппированы все задачи одной доработки + `README.md` с её обзором (DesignReview) + подпапка `done/` для выполненных. |
| **Память (Serena memory)** | Обычные `.md`-файлы в `.serena/memories/` с правилами и паттернами проекта («как мы пишем тесты», «где лежит доступ к БД»). Читаются агентом по мере надобности. [Serena](https://github.com/oraios/serena) — инструмент, дающий агенту удобный поиск по коду и памяти. |
| **CLAUDE.md** | Единый свод правил проекта в корне. Главный источник истины: агенты любых инструментов обязаны его читать (`AGENTS.md` просто перенаправляет на него). |
| **PRD** | *Product Requirements Document* — первичный документ нового проекта: видение, пользователи, пользовательские сценарии, границы функциональности, ограничения и направление архитектуры. Пишется **до** спеки, через интервью (промт `PROMT_PRD` / скилл `/new-prd`), и ложится в `ai-flow/docs/specs/PRD.md`. |
| **Промт (prompt)** | Шаблон-инструкция в `ai-flow/docs/prompts/`. Их семь — дискавери и PRD нового проекта, написание спеки, декомпозиция на задачи, инструкция агенту-исполнителю, наполнение памяти, перенос CI и адаптация флоу под другой инструмент. |
| **Хук (hook)** | Небольшой скрипт, который среда запускает автоматически на событие (здесь — при старте сессии). Единственное настоящее «автоматически» в этом наборе. |
| **Субагент / скилл** | Специализированные помощники Claude Code. Субагенты `prd-author` (интервьюирует и пишет PRD), `task-author` (создаёт задачи), `doc-keeper` (ведёт доки и память) и `task-runner` (запускает оркестратор по фиче); скиллы `/new-prd`, `/new-task`, `/sync-docs` и `/run-tasks` — удобные точки входа к ним. |
| **Маркер завершения** | Строка `<promise>COMPLETE</promise>`, которую агент печатает, закончив задачу. По ней оркестратор понимает, что можно коммитить и двигаться дальше. |
| **Проход проверки фичи** | Отдельный запуск агента (промт `PROMT_VERIFY`) после последней задачи фичи: сборка, весь набор тестов, исправления до зелёного. Тесты при запуске фичи гоняются только здесь, а не после каждой задачи; фича уезжает в архив только после зелёного прохода. |

## Как это работает — общая картина

```
              ВЫ описываете идею нового проекта
                          │
                          ▼
                     PROMT_PRD                ← только для проекта с нуля (/new-prd)
                  (интервью → PRD:
                   видение, пользователи,
                   сценарии, ограничения)
                          │
                          ▼
               ai-flow/docs/specs/PRD.md
                          │
                 ВЫ описываете, что хотите (или берёте это из PRD)
                          │
        ┌─────────────────┼──────────────────────────┐
        ▼                 ▼                            ▼
  PROMT_SERENA        PROMT_SPEC                  PROMT_TASKS
  (наполнить          (написать                  (разбить на
   память проекта)     спецификацию)              атомарные задачи)
        │                 │                            │
        ▼                 ▼                            ▼
 .serena/memories/   ai-flow/docs/specs/    ai-flow/docs/tasks/<фича>/
   *.md + таблица      README + NN-*.md         README (DesignReview)
   в CLAUDE.md                                  + файлы задач
        └───────────┬─────┴───────────────┬──────────┘
                    ▼                      ▼
            python ai-flow/run_tasks.py  (ОРКЕСТРАТОР)
                    │
                    │  для каждой готовой задачи:
                    │   1. собирает промт: PROMT_AGENT + CLAUDE.md +
                    │      указатели на спеки/память + DesignReview +
                    │      журнал + текст задачи
                    │   2. запускает АГЕНТА (claude из agents.yml)
                    │   3. агент пишет тесты (TDD) и код, собирает проект,
                    │      обновляет доки/память, печатает
                    │      <promise>COMPLETE</promise>
                    │   4. оркестратор переносит задачу в done/ и коммитит
                    │
                    │  после последней задачи фичи — ПРОХОД ПРОВЕРКИ:
                    │   PROMT_VERIFY: сборка + весь набор тестов + фиксы
                    │   до зелёного → фича уезжает в tasks/done/, коммит
                    ▼
        Готовый код + обновлённые:
          docs/CHANGELOG.md · docs/specs/<фича>/{README,IMPLEMENTED}.md
          · .serena/memories/* · git-история
```

Ключевая идея: **оркестратор не думает** — он лишь подкладывает агенту весь нужный контекст и следит
за порядком. Всё «мышление» происходит внутри агента, но в жёстких рамках задачи и правил проекта.

Один и тот же `run_tasks.py` работает и локально, и в CI: см.
[Запуск задач в GitHub Actions](#запуск-задач-в-github-actions) — там же промт `PROMT_CI` для
переноса пайплайна на другую CI-систему (GitLab и прочие).

## Что нужно перед стартом (prerequisites)

| Нужно | Зачем | Как проверить/поставить |
|---|---|---|
| **Python 3.10+** | На нём написаны `run_tasks.py` и `init.py`. | `python --version` |
| **PyYAML** | Оркестратор читает конфиг `agents.yml`. | `pip install pyyaml` |
| **Claude Code** | Собственно исполнитель кода — единственный инструмент, под который флоу настроен из коробки. | Установите и авторизуйтесь: [Claude Code](https://docs.claude.com/claude-code). Другой CLI — см. [«Другой инструмент»](#другой-инструмент-не-claude-code). |
| **git** (желательно) | Для авто-коммитов после каждой задачи. Без него оркестратор просто пропустит коммит. | `git --version` |
| **uv / uvx** (желательно) | Запускает сервер памяти [Serena](https://github.com/oraios/serena) из `.mcp.json`. | `pip install uv` или [astral.sh/uv](https://astral.sh/uv) |
| **codebase-memory-mcp** (желательно) | Граф кода (символы, вызовы, архитектура) из `.mcp.json`. | `curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh \| bash` |

> **Минимум, чтобы попробовать:** Python + PyYAML + установленный Claude Code. Serena, граф кода и git
> можно добавить позже — флоу деградирует мягко (память и граф необязательны: память читается как
> обычные `.md`, а граф заменяется чтением файлов; коммиты без git просто не делаются).

## С чего начать (пошагово)

Есть два сценария. Выберите свой.

### Сценарий A. Начать новый проект на базе шаблона (проще всего)

Этот репозиторий **сам является** шаблоном — вся инфраструктура уже на месте. Достаточно взять его за
основу своего проекта:

```bash
# 1. Возьмите шаблон как основу нового проекта (клонирование + отвязка от истории шаблона)
git clone https://github.com/nazarovsa/ai-template.git my-project
cd my-project
rm -rf .git && git init          # начать свою git-историю (по желанию)

# 2. Поставьте зависимость оркестратора
pip install pyyaml

# 3. Проверьте MCP (Serena + граф кода; источник — коммиченный .mcp.json)
python ai-flow/init.py setup-mcp

# 4. Онбординг: пусть агент изучит проект и наполнит память + обзор в specs/README
#    — в Claude Code выполните скилл:
/sync-docs
#    (или вручную скормите агенту ai-flow/docs/prompts/PROMT_SERENA.md)
```

### Сценарий B. Развернуть флоу в отдельную папку / существующий проект

Используйте установщик `init.py` — он копирует все нужные файлы в целевую папку и адаптирует их:

```bash
# новый проект: язык кода + язык общения агента с вами
python ai-flow/init.py init --target ../my-project --lang typescript --comm-lang ru
```

`init` не перезаписывает уже существующие файлы (если не передать `--force`), а `.gitignore` — дополняет.
Подробнее про флаги — в разделе [«Справочник команд»](#справочник-команд).

### Дальше (общее для A и B) — цикл разработки

```bash
# 5. Опишите доработку и разбейте её на задачи (скилл вызывает субагента task-author):
/new-task Добавить вход по email и паролю с выдачей JWT

# 6. Запустите выполнение — агент сделает задачи по очереди:
python ai-flow/run_tasks.py

# 7. Периодически освежайте память/доки, если появились новые паттерны:
/sync-docs
```

> `/new-task` и `/sync-docs` — это **скиллы Claude Code** (набираются в его чате). Работаете в другом
> инструменте — один раз прогоните `ai-flow/docs/prompts/PROMT_TOOL.md` (он создаст такие же точки
> входа в вашем формате) либо скармливайте агенту нужный промт из `ai-flow/docs/prompts/` руками.

## Внедрить в свой проект руками агента

Репозиторий шаблона: **<https://github.com/nazarovsa/ai-template>**

Если у вас уже есть проект и вы не хотите разбираться в установщике вручную — отдайте работу самому
агенту. Ниже два готовых промта: **первый ставит флоу**, **второй настраивает его под ваш код**.
Откройте кодинг-CLI **в корне своего проекта** и скопируйте промт в чат целиком, заменив
плейсхолдеры в угловых скобках. Если ваш CLI — не Claude Code, добавьте третьим шагом
[адаптацию под инструмент](#другой-инструмент-не-claude-code).

### Промт 1 — установка флоу

```text
Установи в этот проект ai-flow — шаблон агентского workflow из https://github.com/nazarovsa/ai-template

Действуй по шагам, ничего не выдумывая; если шаг не удался — остановись и скажи мне.

1. Склонируй шаблон во временную папку ВНЕ проекта:
   git clone --depth 1 https://github.com/nazarovsa/ai-template.git ../ai-template-src

2. Запусти установщик, целясь в корень ТЕКУЩЕГО проекта:
   python ../ai-template-src/ai-flow/init.py init --target . --lang <LANG> --comm-lang <COMM_LANG>
   где <LANG> = основной язык кода проекта (python | typescript | csharp | go | java | rust …),
       <COMM_LANG> = язык, на котором ты говоришь со мной (ru | en | …).
   Флаг --force НЕ используй: установщик намеренно пропускает уже существующие файлы.

3. Скопируй из клона каталог ai-flow/docs/core_templates/ (установщик его не переносит),
   не затирая файлы, если они уже есть.

4. Разбери пропущенные файлы. Установщик пишет «skip (exists)» для того, что уже было в проекте.
   Для моих README.md / CLAUDE.md / AGENTS.md / .gitignore: не заменяй их, а перенеси недостающие
   правила из ../ai-template-src/CLAUDE.md — разделы «Workflow», «Project knowledge»,
   «Implementation rules», «Always-apply rules» — в мой CLAUDE.md, сохранив все мои правила.

5. Проверь результат установки: появились ai-flow/ (run_tasks.py, init.py, agents.yml, docs/),
   .serena/ (project.yml + memories), .mcp.json, .github/workflows/ai-flow-tasks.yml, субагенты и
   скиллы (.claude/agents + .claude/skills). Убедись, что в .claude/settings.json есть
   SessionStart-хук и enabledMcpjsonServers.

6. Поставь зависимость оркестратора и проверь его вхолостую:
   pip install pyyaml
   python ai-flow/run_tasks.py --dry-run

7. Удали временную папку ../ai-template-src.

8. Отчитайся кратко: что скопировано, что пропущено как уже существующее, что я должен решить сам
   (конфликты правил, стек, выбор агента-исполнителя). Ничего не коммить без моего согласия.
```

### Промт 2 — настройка под ваш проект

Запускать после установки. В Claude Code его можно заменить одной командой `/sync-docs` — она делает
то же самое через субагента `doc-keeper`.

```text
Настрой установленный ai-flow под этот проект. Правила бери из CLAUDE.md,
методику — из ai-flow/docs/prompts/PROMT_SERENA.md.

1. Изучи кодовую базу: структура каталогов, точки входа, слои, стек, тесты, конфигурация,
   команды сборки/запуска. Опирайся на реальные файлы, а не на догадки.

2. Заполни память проекта .serena/memories/*.md по найденным паттернам:
   - suggested-commands — настоящие команды сборки, тестов, линта, запуска ИМЕННО этого проекта;
   - task-completion — что здесь считается «задача выполнена»;
   - build-and-verify — как собрать и убедиться, что всё работает;
   - плюс по одной памяти на устойчивый паттерн (слои, доступ к данным, тесты, конфиг, домен).
   Ключевые бизнес-правила домена (формулы, коэффициенты, пороги, инварианты) — в domain-rules.

3. Обнови в CLAUDE.md таблицу «Task trigger → Required call»: по строке на каждую созданную память,
   без строк без памяти и без ссылок на несуществующие файлы.

4. Заполни ai-flow/docs/specs/README.md — обзор проекта: назначение, стек, модули, точки входа,
   окружения, внешние зависимости.

5. Приведи ai-flow/docs/core_templates/ в соответствие с реальным стеком: шаблон, который к проекту
   не относится, — замени описанием НАШИХ правил или удали, поправив раздел «Implementation rules»
   в CLAUDE.md. Ссылок на удалённые файлы остаться не должно.

6. Сверь ai-flow/agents.yml (агент по умолчанию, модель, таймаут задачи) и .serena/project.yml
   (имя проекта, язык) с реальностью.

7. Всё неизвестное — вопрос мне, а не выдумка. В конце покажи список созданных/изменённых файлов.
```

### Что дальше

После двух промтов проект готов к обычному циклу флоу:

```bash
/new-task Добавить вход по email и паролю с выдачей JWT   # или промт ai-flow/docs/prompts/PROMT_TASKS.md
python ai-flow/run_tasks.py
```

| Ситуация | Что учесть |
|---|---|
| Работаете **не** в Claude Code | Прогоните `ai-flow/docs/prompts/PROMT_TOOL.md` под своим инструментом — он создаст роли и точки входа в его формате; см. [раздел](#другой-инструмент-не-claude-code) |
| В проекте уже есть `CLAUDE.md`/`AGENTS.md` | Установщик их не тронет — слияние правил делает агент (шаг 4 промта 1); проверьте результат глазами |

| Уже есть `.codex/`, `.cursor/`, `.gemini/` и т. п. | Установщик их не создаёт и не трогает — их наполняет `PROMT_TOOL` под ваш инструмент |
| Нужен «чистый» старт без существующего кода | Проще [Сценарий A](#сценарий-a-начать-новый-проект-на-базе-шаблона-проще-всего): шаблон клонируется как основа нового проекта |

## Новый проект с нуля: сначала PRD

Если проект **greenfield** (есть идея, но ещё нет ни кода, ни спеки), начните не с задачи, а с
**дискавери** — сбора первичных требований. Для этого есть отдельный агент `prd-author` и скилл
`/new-prd`. Он **проводит интервью**, задавая вопросы по темам, и по ответам пишет
`ai-flow/docs/specs/PRD.md`.

```bash
# в чате Claude Code — запустите интервью (в скобках можно сразу дать грубую идею):
/new-prd Мобильное приложение для учёта личных расходов с распознаванием чеков
```

Агент спросит вас **по секциям** (не вываливая всё сразу) и уточнит:

| Тема | Что выясняет |
|---|---|
| Видение и проблема | что за продукт в одном предложении, чью боль решает и почему сейчас |
| Пользователи и персоны | кто основные/второстепенные пользователи, их контекст и уровень |
| Пользовательские сценарии | 3–7 ключевых сценариев «триггер → шаги → результат»; какой главный |
| Функциональность | возможности, разбитые на **MVP** и «потом»; что явно НЕ входит в v1 |
| Нефункциональные требования и ограничения | производительность, масштаб, безопасность, приватность, комплаенс, бюджет, сроки |
| Направление архитектуры | платформа, стек (или разумный дефолт как допущение), деплой, монолит/сервисы |
| Модель данных | ключевые сущности и связи, источники и чувствительность данных |
| Интеграции | сторонние API/сервисы, авторизация, платежи; жёсткие зависимости vs опциональные |
| Метрики успеха | измеримые сигналы, что продукт работает и полезен |
| Допущения и риски | явные допущения, главные технические/продуктовые/срочные риски |

Правило то же, что и во всём флоу: **агент не выдумывает** — каждое неизвестное становится либо
*Open Question*, либо явным *Assumption* с обоснованием. Готовый `PRD.md` содержит секции: видение,
проблема, цели и метрики, персоны, сценарии, функциональные требования (MVP/потом), нефункциональные
требования, архитектурное направление, модель данных, интеграции, допущения и риски, вне области,
открытые вопросы и **Next Steps**.

**Дальше по PRD:**

```bash
# 1. Превратить области PRD в детальные спеки (промт PROMT_SPEC — вручную скормите его агенту):
#    вход: PRD.md → выход: ai-flow/docs/specs/NN-*.md
# 2. Онбординг новой кодовой базы и наполнение памяти:
/sync-docs
# 3. Декомпозировать первую фичу в задачи:
/new-task <первая фича из PRD>
```

> Интервью **интерактивно**, поэтому, в отличие от `/new-task` и `/sync-docs`, `/new-prd` ведёт диалог
> прямо в основном чате (запущенный субагент не может задавать вам вопросы). Вне Claude Code скормите
> агенту `ai-flow/docs/prompts/PROMT_PRD.md` в его собственной сессии — результат тот же.

## Сквозной пример: фича «вход по логину»

Покажем весь путь на конкретной доработке. Предположим, проект уже онбординжен (шаг 4 выше выполнен).

**1. Описываем и декомпозируем.** В чате Claude Code:

```
/new-task Вход по email+паролю: эндпоинт POST /login, проверка пароля (bcrypt),
выдача JWT на 24 часа, негативные сценарии на неверные креды.
```

Субагент `task-author` прочитает правила проекта и память, возьмёт формат из `PROMT_TASKS.md` и создаст:

```
ai-flow/docs/tasks/202607131500_user-login/
├── README.md                              # DesignReview: суть, ценность, архитектура, критерии
├── 202607131500_add-login-endpoint.md     # задача 1: эндпоинт + DTO
├── 202607131505_verify-password.md         # задача 2: проверка пароля (Depends on: add-login-endpoint)
└── 202607131510_issue-jwt.md               # задача 3: выдача JWT     (Depends on: verify-password)
```

**2. (Опционально) смотрим план без запуска:**

```bash
python ai-flow/run_tasks.py --feature user-login --dry-run
```

**3. Запускаем выполнение только этой фичи:**

```bash
python ai-flow/run_tasks.py --feature user-login
```

Оркестратор для каждой задачи по очереди (учитывая `Depends on:`):

- соберёт агенту промт (правила, память, DesignReview фичи, журнал, текст задачи);
- запустит агента — тот прочитает существующий код, напишет тесты по `## Test Cases` и реализацию,
  соберёт проект (тесты в прогоне фичи **не запускает**), допишет `CHANGELOG.md`, обновит
  `specs/202607131500_user-login/{README,IMPLEMENTED}.md`;
- увидев `<promise>COMPLETE</promise>`, **перенесёт** файл задачи в `202607131500_user-login/done/`
  и сделает коммит `feat: task #202607131500_add-login-endpoint - Add login endpoint`.

После последней задачи оркестратор запускает **проход проверки фичи**: агент собирает проект, гоняет
весь набор тестов, чинит упавшее и повторяет до зелёного. Только после зелёного прохода фича уезжает
в архив `ai-flow/docs/tasks/done/` отдельным коммитом `test: feature #202607131500_user-login - tests green`.
Тесты гоняются один раз на фичу, а не после каждой задачи (подробнее —
[гейт тестов](#как-устроен-оркестратор-под-капотом)).

**4. Что осталось после прогона:**

- рабочий код + тесты в проекте, весь набор тестов зелёный;
- `ai-flow/docs/tasks/done/202607131500_user-login/` — фича в архиве, все три задачи в её `done/`;
- `ai-flow/docs/specs/202607131500_user-login/README.md` (цель) и `IMPLEMENTED.md` (как сделано);
- дописанный `ai-flow/docs/CHANGELOG.md`;
- при появлении паттерна (напр., «как мы валидируем DTO») — новая запись в `.serena/memories/` и
  строка в таблице `CLAUDE.md`;
- четыре коммита в git: три задачи + проход проверки.

Если во время работы всплыл общий паттерн, освежите знания: `/sync-docs`.

## Структура репозитория

```
<repo>/
├── README.md              # этот файл — как пользоваться флоу
├── CLAUDE.md              # ЕДИНЫЙ свод правил + таблица read_memory(...) (на English)
├── AGENTS.md              # редирект прочих инструментов на CLAUDE.md + указание на PROMT_TOOL
├── .mcp.json              # MCP-серверы проекта: serena + codebase-memory-mcp (граф кода)
├── .claude/
│   ├── settings.json      # сюда init.py вписывает SessionStart-хук + enabledMcpjsonServers
│   ├── agents/            # субагенты: prd-author (PRD), task-author (задачи), doc-keeper (доки/память), task-runner (запуск)
│   └── skills/            # скиллы: new-prd, new-task, sync-docs, run-tasks (тонкие обёртки над субагентами)
├── .serena/
│   ├── project.yml        # конфиг Serena (язык проекта задаётся здесь)
│   └── memories/          # ПАМЯТЬ проекта — обычные .md (suggested-commands, task-completion, …)
├── .github/
│   └── workflows/
│       └── ai-flow-tasks.yml  # CI: запуск задач в GitHub Actions с созданием PR
└── ai-flow/               # ВСЯ инфраструктура флоу
    ├── run_tasks.py       # ОРКЕСТРАТОР авто-выполнения задач
    ├── init.py            # УСТАНОВЩИК: развернуть флоу в проект + проверить MCP
    ├── agents.yml         # конфиг агента-исполнителя (claude) и оркестратора
    ├── hooks/
    │   ├── check_memory_sync.py    # хук: сверяет таблицу в CLAUDE.md с файлами памяти
    │   └── hooks.config.json       # настройки хука
    └── docs/
        ├── prompts/       # 8 промтов: PROMT_PRD / PROMT_SPEC / PROMT_TASKS / PROMT_AGENT / PROMT_VERIFY / PROMT_SERENA / PROMT_CI / PROMT_TOOL
        ├── core_templates/# НОРМАТИВНЫЕ правила реализации: backend_template / frontend_template
        ├── specs/         # спеки + функциональность: root README + <feature>/{README,IMPLEMENTED}
        ├── tasks/         # задачи по фичам: <YYYYMMddHHmm_FEATURE>/{README, задачи, done/}
        └── CHANGELOG.md   # хронологический журнал выполненных задач
```

**Как читать эту структуру.** Всё, что нужно инструменту «из коробки» (правила и авто-обнаружение),
живёт в корне и в `.claude/`/`.serena/`. Всё, что относится к самому процессу (скрипты,
промты, задачи, спеки, журнал) — под `ai-flow/`. Такое разделение позволяет
[не тащить флоу в git](#не-коммитить-флоу-в-git),
если он вам нужен только локально.

### Шаблоны реализации — `core_templates/`

В отличие от промтов (инструкции агенту на один шаг флоу), шаблоны в `ai-flow/docs/core_templates/` —
**нормативные правила кода**, действующие постоянно. Они подключены в `CLAUDE.md` разделом
«Implementation rules» и обязательны к соблюдению при написании кода.

| Шаблон | Покрывает | Читать перед |
|---|---|---|
| `backend_template.md` | .NET 10: структура решения, слои, домен, EF Core, сервисы, HTTP API, JWT-аутентификация с ролями, ошибки, опции, DI, тесты, сборка | правкой любого `.cs`, `.csproj`, миграции |
| `frontend_template.md` | Next.js App Router: дерево каталогов, правила слоёв и импортов, доступ к данным, состояние, i18n, стили | правкой любого `.ts`/`.tsx` |

Оба заканчиваются чек-листом новой фичи и списком анти-паттернов — чек-лист проходится перед
сдачей, анти-паттерны блокируют ревью. Проект на другом стеке удаляет неприменимый шаблон или
заменяет его своим, но фиксирует замену в `CLAUDE.md`, а не оставляет правило висеть в пустоту.

### Роли восьми промтов

| Промт | Вход | Выход | Когда запускать |
|---|---|---|---|
| `PROMT_PRD.md` | идея нового проекта | PRD `specs/PRD.md` (через интервью) | **старт проекта с нуля** (`/new-prd`) |
| `PROMT_SERENA.md` | код проекта | память `.serena/memories/*` + таблица в `CLAUDE.md` + обзор в `specs/README` | **онбординг** и когда доки отстали (`/sync-docs`) |
| `PROMT_SPEC.md` | требования | файлы спеки `specs/NN-*.md` | когда нужна детальная спецификация перед декомпозицией |
| `PROMT_TASKS.md` | спека/требования | фича-папка с DesignReview + задачами | на каждую новую доработку (`/new-task`) |
| `PROMT_AGENT.md` | одна задача (+ контекст) | реализованный код | **автоматически** — его использует оркестратор, вручную не запускают |
| `PROMT_VERIFY.md` | выполненная фича (все её задачи) | зелёные сборка и весь набор тестов, исправления | **автоматически** — оркестратор запускает после последней задачи фичи |
| `PROMT_CI.md` | название целевой CI-системы | пайплайн для неё (GitLab CI, Jenkins, …) | когда нужен запуск задач не в GitHub Actions |
| `PROMT_TOOL.md` | инструмент, из-под которого его запустили | роли, точки входа, хук, MCP и запись в `agents.yml` в формате этого инструмента | **один раз**, если работаете не в Claude Code |

## Справочник команд

### Оркестратор — `run_tasks.py`

Выполняет готовые задачи по очереди. Требует `pip install pyyaml`.

```bash
python ai-flow/run_tasks.py                      # агент по умолчанию из agents.yml (claude/sonnet)
python ai-flow/run_tasks.py --model opus         # другая модель того же агента
python ai-flow/run_tasks.py --agent <name>       # другой агент — если он добавлен в agents.yml (PROMT_TOOL)
python ai-flow/run_tasks.py --feature user-login # только задачи из папок фич, где имя совпадает
python ai-flow/run_tasks.py --task add-login     # только задачи, чьё имя содержит подстроку
python ai-flow/run_tasks.py --dry-run            # показать план, ничего не выполняя
python ai-flow/run_tasks.py --config path.yml    # свой конфиг вместо ai-flow/agents.yml
```

| Флаг | Что делает |
|---|---|
| `--agent NAME` | имя агента из `agents.yml` (перекрывает `default_agent`) |
| `--model M` | перекрывает модель выбранного агента |
| `--feature NAME` | запускать только задачи из фича-папок, где `NAME` — подстрока имени |
| `--task NAME` | запускать только задачи, где `NAME` — подстрока имени файла; после одной задачи стоп |
| `--dry-run` | вывести, что и в каком порядке запустилось бы, без запуска агента |
| `--config PATH` | путь к альтернативному `agents.yml` |

### Установщик — `init.py`

Разворачивает флоу в целевую папку. Настраивает **Claude Code**; под другой инструмент флоу
адаптирует не установщик, а промт [`PROMT_TOOL`](#другой-инструмент-не-claude-code).

```bash
# развернуть в новую папку: язык кода + язык общения
python ai-flow/init.py init --target ../my-project --lang typescript --comm-lang ru

# развернуть в текущую папку
python ai-flow/init.py init

# только проверить MCP (Serena + граф кода)  (алиас: setup-serena)
python ai-flow/init.py setup-mcp
```

Флаги `init`:

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--target DIR` | `.` | куда разворачивать |
| `--lang LANG` | `python` | язык проекта — прописывается в `.serena/project.yml` |
| `--comm-lang LANG` | `en` | язык, на котором агент говорит с вами (строка в `CLAUDE.md`) |
| `--force` | — | перезаписывать уже существующие файлы |
| `--no-serena` | — | пропустить шаг проверки MCP (Serena + граф кода) |

Что делает `init` по шагам: копирует набор файлов, включая `.mcp.json` (пропуская существующие без
`--force`) → проставляет язык проекта и язык общения → дополняет `.gitignore` → вписывает в
`.claude/settings.json` SessionStart-хук **и** `enabledMcpjsonServers` (доверие серверам из
`.mcp.json`) → проверяет MCP (если не `--no-serena`).

### Скиллы Claude Code (набираются в чате)

| Скилл | Делегирует | Результат |
|---|---|---|
| `/new-prd [грубая идея]` | субагенту **prd-author** | интервью по темам → PRD `ai-flow/docs/specs/PRD.md` (видение, пользователи, сценарии, ограничения, архитектура) |
| `/new-task <описание или ссылка на спеку>` | субагенту **task-author** | новая фича-папка в `ai-flow/docs/tasks/` с DesignReview и файлами задач |
| `/sync-docs` | субагенту **doc-keeper** | наполнение/обновление памяти `.serena/memories/*`, спеков и таблицы в `CLAUDE.md` |
| `/run-tasks <фича>` | субагенту **task-runner** | запуск `run_tasks.py` по фиче: все её задачи подряд или только следующую |

Скиллы `/new-task`, `/sync-docs` и `/run-tasks` намеренно «тонкие» — вся логика в субагентах. `/new-prd` ведёт
**интерактивное** интервью прямо в чате (субагент не может задавать вопросы пользователю). Вне Claude
Code эти же четыре точки входа создаёт `PROMT_TOOL` в формате вашего инструмента; без адаптации
используйте промты напрямую: `PROMT_PRD.md` вместо `/new-prd`, `PROMT_TASKS.md` вместо `/new-task`,
`PROMT_SERENA.md` вместо `/sync-docs`.

## Как устроен оркестратор (под капотом)

Понимание внутренностей помогает отлаживать. Вот что делает `run_tasks.py` на каждом цикле:

1. **Находит задачи.** Сканирует `ai-flow/docs/tasks/`, берёт каждую фича-папку (кроме скрытых),
   внутри — все `*.md`, кроме `README.md`. Порядок — по имени файла (префикс-таймстамп = хронология).
2. **Определяет выполненные.** Задачи, лежащие в `<фича>/done/`, считаются готовыми.
3. **Проверяет зависимости.** Строка `Depends on:` / `Зависит от:` в файле задачи ссылается на другие
   задачи по имени/подстроке. Задача «готова к запуску», только если все её зависимости уже в `done/`.
4. **Собирает промт** из: `PROMT_AGENT.md` + `CLAUDE.md` + указателей на спеки и память (по умолчанию
   именно указатели, не полный текст — агент дочитает нужное сам) + DesignReview фичи + последнего
   `CHANGELOG.md` + текста самой задачи + напоминаний.
5. **Запускает агента.** Команда берётся из `agents.yml` (например,
   `claude --model sonnet --print --dangerously-skip-permissions`). Промт передаётся через stdin
   (временный файл), вывод стримится в консоль. Рабочая директория — корень проекта, так что агент
   видит весь код, а не только `ai-flow/`.
6. **Определяет успех.** Успех = в выводе есть маркер `<promise>COMPLETE</promise>` **или** агент вышел
   с кодом 0. Иначе — провал.
7. **Фиксирует результат.** При успехе: **переносит** файл задачи в `<фича>/done/` и (если это git-репо
   и коммиты включены) делает коммит одной строкой `feat: task #{id} - {title}`, обрезая до 155 символов,
   без упоминаний ИИ/инструментов.
8. **Закрывает фичу проходом проверки.** Когда у фичи не осталось задач, оркестратор запускает агента
   с `PROMT_VERIFY.md`: сборка, **весь** набор тестов, исправления и повтор до зелёного. Здесь маркер
   обязателен — выход с кодом 0 без маркера считается провалом. Только зелёный проход переносит папку
   фичи в `tasks/done/` и коммитит `test: feature #{feature} - tests green`. Фича, у которой все задачи
   в `done/`, но которая не в архиве, считается непроверенной: следующий запуск сначала проверяет её.
9. **Обрабатывает сбои.** Три провала подряд (задачи или прохода проверки) — остановка. Тайм-аут
   задачи (по умолчанию 1200 с) — провал этой задачи; у прохода проверки свой `verify_timeout`.

**Гейт тестов: единица работы — то, что запросили** (`test_gate` в `agents.yml`, по умолчанию
`feature`). Прогон тестов после каждой задачи съедает время и лимиты, поэтому при запуске фичи
(без `--task`) задачи пишут тесты по TDD и обязаны компилироваться, но тесты запускаются один раз —
в проходе проверки после последней задачи. Гейт «зелёные тесты» при этом не ослаблен: его единицей
стала фича, а не подзадача. При `--task` единица — задача: она сама гоняет тесты (а если закрыла
фичу, за ней всё равно идёт проход проверки). `test_gate: task` возвращает прогон тестов в каждую
задачу. Нарезка задач от этого не меняется: каждая по-прежнему проектируется так, чтобы после неё
тесты были зелёными (`PROMT_TASKS.md` §0).

> Важные нюансы: агенту **запрещено** самому делать `git commit` — это делает оркестратор. Файл задачи в
> `done/` и папку фичи в архив переносит тоже оркестратор, а не агент. Маркер завершения агент печатает
> сам по инструкции из `PROMT_AGENT.md` (задача) или `PROMT_VERIFY.md` (проход проверки).

## Модель задач и документации

**Задачи группируются по доработкам.** Одна папка = одна доработка (фича или фикс — не важно):

```
ai-flow/docs/tasks/
├── MILESTONES.md                      # ключевые этапы реализации (план над фичами)
└── <YYYYMMddHHmm_FEATURE_NAME>/
    ├── README.md                      # DesignReview: суть, ценность, архитектура, критерии
    ├── <YYYYMMddHHmm_TASK_SUMMARY>.md  # один файл = одна атомарная задача
    └── done/                          # сюда run_tasks.py переносит выполненные (не создавайте вручную)
```

- `YYYYMMddHHmm` — таймстамп. Получить: `date +%Y%m%d%H%M` (Linux/macOS) или
  `Get-Date -Format yyyyMMddHHmm` (PowerShell на Windows).
- `FEATURE_NAME` / `TASK_SUMMARY` — kebab-case; сводка задачи ≤ 5 английских слов.
- Порядок выполнения = порядок имён; `Depends on:` уточняет зависимости.
- Заголовок задачи = первый `#`-заголовок в файле (по нему парсер берёт название).
- `README.md` внутри фича-папки задачей **не считается** — это её DesignReview.
- Каждая задача обязана содержать секцию `## Test Cases` — тест-кейсы пишутся **до** реализации,
  только unit-уровень (внешние зависимости мокируются), минимум — hot-paths и корнер-кейсы.

**Над фичами есть слой планирования — ключевые этапы.** PRD не режется в задачи целиком: сначала он
делится на этапы, каждый из которых даёт проверяемую возможность («вход работает и каналы
подтягивают статистику», «покупатель находит папку и получает контакт»), и этапы записываются в
`ai-flow/docs/tasks/MILESTONES.md` — цель, покрытые требования и спеки, входящие фичи, критерии
завершения, статус. Файл лежит рядом с фича-папками, а не внутри них: выполненная фича уезжает в
архив, а план должен остаться.

Последняя задача последней фичи каждого этапа — **контрольная задача сверки**: она не меняет
продуктовый код, а сверяет PRD и спеки с фактической реализацией, исправляет разошедшееся, закрывает
отвеченные открытые вопросы, обновляет `MILESTONES.md` и только после этого нарезает задачи
следующего этапа. Смысл прост: нарезка задач читает текст спек, и если спеки отстали от кода, ошибку
унаследует каждая следующая задача. Правила — `PROMT_TASKS.md` §11.

**Спецификации и функциональность** живут вместе в `ai-flow/docs/specs/` (без отдельной папки
`functionality/`):

- корневой `README.md` — обзор проекта (заполняется при онбординге, разделы Overview/Capabilities);
- по папке на реализованную фичу: `README.md` — **целевое** поведение (что должно быть),
  `IMPLEMENTED.md` — **как реализовано** по факту. Обновляются автоматически после задач.

**Журнал** `ai-flow/docs/CHANGELOG.md` — только хронология («что и когда сделано»).
Переиспользуемые паттерны в журнал **не** пишутся — они идут в память Serena (единое хранилище знаний).

Полные шаблоны DesignReview и файла задачи — в `ai-flow/docs/tasks/README.md` и `PROMT_TASKS.md`.

## Конфигурация: agents.yml

`ai-flow/agents.yml` настраивает и оркестратор, и доступных агентов. Разбор по полям:

```yaml
default_agent: claude          # агент по умолчанию (если не передан --agent)
task_timeout: 1200             # тайм-аут одной задачи, секунд
completion_marker: "<promise>COMPLETE</promise>"   # что печатает агент по завершении
test_gate: feature             # feature → тесты раз на фичу (проход проверки); task → в каждой задаче
verify_timeout: 2400           # тайм-аут прохода проверки фичи, секунд (по умолчанию 2 × task_timeout)

git:
  enabled: true                # false → не коммитить; авто-пропуск, если это не git-репо
  auto_commit: true
  message_template: "feat: task #{id} - {title}"   # обрезается до ≤155 символов, без упоминаний ИИ
  verify_message_template: "test: feature #{feature} - tests green"   # коммит прохода проверки

context:                       # все пути — относительно корня проекта
  tasks_dir: ai-flow/docs/tasks
  specs_dir: ai-flow/docs/specs
  memories_dir: .serena/memories
  changelog_file: ai-flow/docs/CHANGELOG.md
  agent_prompt: ai-flow/docs/prompts/PROMT_AGENT.md
  verify_prompt: ai-flow/docs/prompts/PROMT_VERIFY.md   # промт прохода проверки фичи
  inline_memories: false       # false → подкладывать указатели на память; true → полный текст

agents:
  claude:                      # Claude Code — единственный агент из коробки
    command: "claude --model {model} --print --dangerously-skip-permissions"
    model: sonnet
```

- `{model}` в строке `command` подставляется из `model` агента или флага `--model`.
- **Другой CLI добавляется сюда отдельной записью** — но не руками «по аналогии»: запустите
  `ai-flow/docs/prompts/PROMT_TOOL.md` под этим инструментом, он сверит реальные флаги его headless-режима
  (`--help`), прогонит smoke-тест и допишет запись сам. Сам оркестратор от инструмента не зависит:
  меняется только строка `command`.
- Если CLI не умеет читать промт из stdin, в `command` ставится плейсхолдер `{prompt_file}` —
  оркестратор запишет промт во временный файл и подставит его путь.
- `inline_memories: true` полезно для агентов без доступа к Serena MCP — тогда весь текст памяти
  вставляется прямо в промт (дороже по токенам, но не требует MCP).

## Запуск задач в GitHub Actions

Тот же оркестратор можно запускать в CI: workflow **`ai-flow · run tasks`**
(`.github/workflows/ai-flow-tasks.yml`) выполняет невыполненные задачи и открывает **Pull Request**
с результатом. Локальный и CI-запуск — это один и тот же `run_tasks.py`, так что поведение совпадает.

### Шаг 1. Получите токен подписки

Claude Code в CI авторизуется долгоживущим OAuth-токеном (живёт год, требует подписки Pro/Max/Team/
Enterprise). Сгенерируйте его **локально**:

```bash
claude setup-token
```

Команда проведёт вас через OAuth и **напечатает токен, никуда его не сохранив** — скопируйте вывод.

### Шаг 2. Положите токен в секреты репозитория

`Settings → Secrets and variables → Actions → New repository secret`:

| Имя секрета | Значение |
|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | вывод `claude setup-token` |

Больше ничего настраивать не нужно: `GITHUB_TOKEN` для коммитов и PR Actions выдаёт сам.

### Шаг 3. Запустите

Вкладка `Actions` → `ai-flow · run tasks` → `Run workflow`. Или из консоли:

```bash
# все невыполненные задачи
gh workflow run ai-flow-tasks.yml

# только одна фича, конкретная модель, PR сразу готовый (не draft)
gh workflow run ai-flow-tasks.yml \
  -f feature=user-login \
  -f model=claude-sonnet-5 \
  -f draft_pr=false

# посмотреть план, ничего не выполняя
gh workflow run ai-flow-tasks.yml -f dry_run=true
```

### Параметры запуска

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `feature` | пусто | выполнить все задачи совпадающей фича-папки (`--feature`) — все они попадают в одну ветку от `main` и один PR |
| `task` | пусто | выполнить одну задачу по имени/подстроке (`--task`); приоритетнее `feature` |
| `agent` | `claude` | агент из `agents.yml` |
| `model` | пусто | переопределить модель; пусто = значение из `agents.yml` |
| `dry_run` | `false` | показать план без выполнения (не будет ни коммитов, ни PR) |
| `draft_pr` | `true` | открыть PR как черновик |

### Что происходит внутри

1. Проверяется секрет `CLAUDE_CODE_OAUTH_TOKEN` — без него запуск падает сразу с понятной ошибкой.
2. Ставятся Node 22, Python 3.12, `pyyaml`, `uv`, CLI `@anthropic-ai/claude-code` и бинарь
   `codebase-memory-mcp` — так поднимаются оба MCP-сервера из `.mcp.json` (Serena + граф кода).
3. Создаётся **одна** ветка от ветки, на которой запустили workflow (обычно `main`): при указанной
   фиче — `ai-flow/<фича>-<run_id>`, иначе `ai-flow/run-<run_id>-<attempt>`.
4. Проверяются MCP-серверы (`claude mcp list`, не фатально) и **прогревается граф кода**
   (`index_repository --mode fast`, не фатально) — обе операции best-effort, результат идёт в Job
   Summary.
5. Из **корня репозитория** выполняется `python ai-flow/run_tasks.py …` — каждая выполненная подзадача
   переезжает в `done/` и коммитится в **эту же ветку** (это делает сам оркестратор).
6. Если появились коммиты — ветка пушится и открывается **один** PR со списком выполненных задач и
   коммитов. То есть все подзадачи фичи попадают в одну ветку от `main` и один PR.

### Важные детали

- **Всё выполняется из корня репозитория** (`defaults.run.working-directory`). Это обязательное
  условие: Claude Code авто-обнаруживает `CLAUDE.md`, `.claude/agents/`, `.claude/skills/` и
  `.claude/settings.json` именно в рабочей директории.
- **Не добавляйте `--bare`** в команду агента в `agents.yml`. Этот флаг ускоряет старт, но отключает
  как раз то авто-обнаружение (правила, субагенты, скиллы, хуки) — и вдобавок **не читает**
  `CLAUDE_CODE_OAUTH_TOKEN`, так что запуск ещё и не авторизуется.
- **`ANTHROPIC_API_KEY` перебивает токен подписки.** По приоритету аутентификации Claude Code
  API-ключ стоит выше `CLAUDE_CODE_OAUTH_TOKEN`. Если задать оба, работа пойдёт по поштучной оплате
  API. Не задавайте `ANTHROPIC_API_KEY` в CI, если хотите расходовать лимиты подписки.
- **MCP в CI поднимается из `.mcp.json`.** Оба сервера — Serena (через `uvx`) и граф кода
  (`codebase-memory-mcp`) — объявлены в коммиченном `.mcp.json`, а `.claude/settings.json` доверяет им
  через `enabledMcpjsonServers`, иначе под `--dangerously-skip-permissions` они бы не стартовали. Тот
  же `.mcp.json` работает и **локально**. Провижининг в CI (установка `uv`/бинаря, `claude mcp list`,
  прогрев графа) — **best-effort**: если сервер не поднялся, память всё равно читается как обычные
  `.md` из `.serena/memories/`, а граф заменяется чтением файлов, и запуск не падает. Нужен полный
  текст памяти в промте — включите `inline_memories: true` в `agents.yml`.
- **Имя проекта графа = имя репозитория.** Прогрев вызывает `index_repository` с `name`, равным имени
  GitHub-репо: `codebase-memory-mcp` по умолчанию выводит имя из basename пути, так что хардкод имени
  заставил бы агента обращаться к пустому графу под другим именем.
- **Пустая очередь — не ошибка.** Если невыполненных задач нет, workflow честно завершается зелёным
  с пометкой «nothing to do» (сам `run_tasks.py` в этом случае выходит с кодом 1 — CI это учитывает).
- **Частичный результат сохраняется.** Если оркестратор упал на середине, PR всё равно создастся из
  успевших задач, с предупреждением в теле, а сам run будет помечен красным.
- **PR, созданный `GITHUB_TOKEN`, не запускает другие workflow** — это ограничение GitHub. Если на PR
  должны срабатывать проверки, используйте GitHub App (`actions/create-github-app-token`) или PAT.
- **Только агент `claude`** ставится в CI. Для другого CLI (добавленного в `agents.yml` через
  `PROMT_TOOL`) допишите установку его бинаря в шаг `Install the toolchain` и имя агента в опции
  параметра `agent`.
- Параллельные запуски на одной ветке сериализуются (`concurrency`) — задачи двигают общие файлы.

### Другая CI-система: GitLab CI, Jenkins и прочие

Готовый пайплайн есть только для GitHub Actions, но сам оркестратор от CI не зависит: `run_tasks.py`
ничего не знает про GitHub. Чтобы получить пайплайн для другой системы, отдайте агенту промт
**`ai-flow/docs/prompts/PROMT_CI.md`** — например, в чате Claude Code:

```
Выполни ai-flow/docs/prompts/PROMT_CI.md

1. Target CI: GitLab CI (SaaS, gitlab.com)
2. Runner: docker, образ ubuntu:24.04
3. Review target: main
4. Keep the GitHub Actions workflow? yes
```

Промт даёт агенту эталонную реализацию (`.github/workflows/ai-flow-tasks.yml`) и **13 инвариантов**,
которые обязаны пережить перенос, — это добытые на практике грабли, а не пожелания. Главные из них:
запуск из корня репозитория; запрет `--bare`; авторизация через `CLAUDE_CODE_OAUTH_TOKEN` и запрет
`ANTHROPIC_API_KEY`; коммитит оркестратор, а не пайплайн; пустая очередь — это успех, а не падение;
частичный результат всё равно едет в MR. Если целевая система какой-то инвариант выразить не может,
агент обязан не умолчать, а описать пробел в отчёте.

Промт запрещает агенту сочинять синтаксис по аналогии: он должен сверить каждое ключевое слово с
актуальной документацией целевой CI и честно пометить всё, что подтвердить не удалось. Итог агент
кладёт по конвенции целевой системы (`.gitlab-ci.yml`, `Jenkinsfile`, …), **вливаясь** в уже
существующий пайплайн, если он есть, и попутно правит `init.py`, `README.md` и `CLAUDE.md`.

`run_tasks.py` при этом менять нельзя — вся разница между CI-системами живёт в файле пайплайна.

## Память проекта (Serena)

**Что это.** [Serena](https://github.com/oraios/serena) — MCP-сервер, который даёт агенту умный поиск и
навигацию по коду (символы, ссылки) и удобную работу с *памятью* проекта. Память — это обычные `.md`-файлы
в `.serena/memories/`, поэтому она **читается напрямую даже без MCP**; MCP нужен лишь для удобства.

**Что уже поставляется** (не удалять, только расширять):

- `suggested-commands` — какие команды флоу запускать и что где лежит;
- `task-completion` — критерий «задача выполнена» (сборка, тесты, журнал, обновление доков).

**Как наполнять память проекта.** Запустите онбординг — субагент `doc-keeper` по `PROMT_SERENA.md`:
изучит код, выделит устойчивые паттерны (архитектура, тесты, доступ к БД, сборка…), запишет их
как память и пропишет строки `read_memory(...)` в таблицу «Project knowledge» в `CLAUDE.md`.

```
/sync-docs
```

**Как настроить MCP.** Источник — коммиченный `.mcp.json` (serena + граф кода), а доверие им
прописано в `.claude/settings.json` (`enabledMcpjsonServers`). Проверить окружение:

```bash
python ai-flow/init.py setup-mcp    # алиас: setup-serena; или на этапе init
```

Команда убеждается, что `.mcp.json` на месте, а `uvx` и бинарь `codebase-memory-mcp` доступны на PATH
(иначе подсказывает, как поставить). Ставить серверы вручную для Claude Code не нужно — их поднимает
`.mcp.json`. Другие инструменты этот файл **не читают** и держат MCP в собственном конфиге
(`.codex/config.toml`, `.cursor/mcp.json`, …) — их прописывает `PROMT_TOOL` при адаптации; после
этого обычно нужна новая сессия инструмента, чтобы MCP-инструменты появились в её наборе.
Документация: <https://github.com/oraios/serena>, <https://github.com/DeusData/codebase-memory-mcp>.

## Хук синхронизации памяти

`ai-flow/hooks/check_memory_sync.py` следит, чтобы таблица `read_memory(...)` в `CLAUDE.md` и реальные
файлы в `.serena/memories/` не разъезжались, и предупреждает о:

- **висячих строках** — таблица ссылается на память, которой нет;
- **сиротах** — файл памяти есть, но в таблице на него нет строки.

Это **best-effort напоминание** (не блокирует), запускается как `SessionStart`-хук — при старте сессии.
`init.py` подмешивает его в существующий `.claude/settings.json`, не затирая другие хуки. В другом
инструменте хук регистрирует `PROMT_TOOL` в его собственном конфиге хуков.

Настройки — `ai-flow/hooks/hooks.config.json`, секция `memory_sync`:

| Ключ | Значение | Смысл |
|---|---|---|
| `enabled` | `true`/`false` | главный выключатель |
| `mode` | `"warn"`/`"off"` | warn — печатает уведомление; off — молчит |
| `check_dangling` | `true`/`false` | сообщать про строки таблицы без файла памяти |
| `check_orphans` | `true`/`false` | сообщать про файлы памяти без строки в таблице |
| `ignore_memories` | список | какие записи не считать «сиротами» (по умолчанию поставляемые) |

Полностью отключить — `mode: "off"` или убрать блок `SessionStart` из `.claude/settings.json`.
Сделать блокирующим — зарегистрировать на gating-событие и возвращать `exit(2)` при проблемах.

> **Три уровня «строгости» инструкций** полезно различать: комментарий в `CLAUDE.md` — пассивная заметка;
> правило-буллет — агент следует ему по мере работы; **хук — единственное детерминированное «автоматически»**
> (запускает сама среда, а не агент).

## Языки

Различают два языка:

- **Язык артефактов флоу** (промты, субагенты, скиллы, память) — всегда **English**. Так шаблон остаётся
  универсальным и переносимым между инструментами.
- **Язык общения** — как агент разговаривает с вами. Задаётся `init.py --comm-lang` и живёт строкой
  `**Communication language: …**` в `CLAUDE.md`. Меняется в любой момент правкой этой строки.

Язык самого проекта (для навигации Serena) задаётся `--lang` и пишется в `.serena/project.yml`.

## Другой инструмент, не Claude Code

Шаблон настроен под **Claude Code** и только под него: субагенты `.claude/agents/`, скиллы
`.claude/skills/`, `SessionStart`-хук в `.claude/settings.json`, MCP из `.mcp.json`. Адаптеров под
Codex/Cursor/Gemini/zcode в репозитории больше нет — вместо них один промт, который делает адаптацию
на вашей стороне, под ту версию CLI, которая у вас реально стоит.

**Что при этом работает и без адаптации** (это просто файлы, их читает любой агент): правила
`CLAUDE.md` (+ редирект `AGENTS.md`), промты `ai-flow/docs/prompts/`, задачи и спеки
`ai-flow/docs/`, память `.serena/memories/*.md`, оркестратор `python ai-flow/run_tasks.py`.
Не работает без адаптации: скиллы `/new-prd`, `/new-task`, `/sync-docs`, `/run-tasks`, субагенты,
хук синхронизации памяти, автоподъём MCP-серверов.

### Как адаптировать

Откройте **свой** агентский CLI в корне проекта (важно: именно тот, под который адаптируем — промт
исследует инструмент, в котором запущен) и дайте ему такой промт:

```text
Выполни ai-flow/docs/prompts/PROMT_TOOL.md — адаптируй ai-flow под инструмент, в котором ты запущен.

1. Инструмент: <название и версия твоего CLI — возьми из его --version>
2. Делать этот инструмент исполнителем задач в ai-flow/agents.yml: да
3. Оставить файлы Claude Code (.claude/, .mcp.json): да
```

Промт заставляет агента **сначала проверить** (через `--help` и актуальную документацию), что его
инструмент реально умеет: субагентов, скиллы/команды, хуки, MCP, headless-режим. Ничего не
поддерживается — он не подделывает, а пишет об этом в отчёте. Дальше он:

| Кусок флоу | Что делает `PROMT_TOOL` |
|---|---|
| Правила | файл-инструкцию инструмента делает **редиректом** на `CLAUDE.md` (не копией) |
| 4 роли (`prd-author`, `task-author`, `doc-keeper`, `task-runner`) | перекладывает в нативный формат; если субагентов нет — вшивает тело роли в точку входа целиком |
| 4 точки входа (`/new-prd`, `/new-task`, `/sync-docs`, `/run-tasks`) | создаёт как скиллы/команды инструмента с теми же триггерами |
| Хук `check_memory_sync.py` | регистрирует на событие старта сессии (включив хуки, если они выключены) |
| MCP (serena + граф кода) | прописывает в собственный конфиг инструмента, добавляет доверие/аппрув |
| `agents.yml` | добавляет запись агента-исполнителя с проверенной командой headless-запуска |
| Доки | обновляет `CLAUDE.md`, `README.md`, память `suggested-commands`, `CHANGELOG.md`, `MANIFEST` в `init.py` |

Что он **не** имеет права сломать (инварианты промта): `CLAUDE.md` остаётся единственным источником
правил, `.claude/` не удаляется, `run_tasks.py` не правится, агент-исполнитель не делает коммитов
и печатает `<promise>COMPLETE</promise>`, память остаётся читаемой как обычные `.md` даже без MCP.

В конце промт требует **проверку, а не рассуждения**: инструмент должен увидеть все четыре точки
входа своей же командой, хук — сработать, `python ai-flow/run_tasks.py --dry-run` — отработать, а
команда исполнителя — пройти smoke-тест (запуск с промтом «напечатай маркер», без правок репозитория).

> Тонкий момент, на котором уже спотыкались: «Claude-совместимый» инструмент всё равно обычно **не
> читает** `.mcp.json` и `.claude/settings.json` и не видит субагентов из `.claude/agents/` — тонкий
> скилл-роутер у него превращается в ссылку в никуда. Поэтому промт требует вшивать тело роли, если
> субагентов нет. И ещё: хуки во многих CLI по умолчанию выключены — регистрация хука в конфиге без
> включения даёт тишину, а не ошибку.

## Не коммитить флоу в git

Если не нужно тащить флоу в репозиторий, исключите весь набор (`ai-flow/`, `.claude/`, `.serena/`,
`CLAUDE.md`, `AGENTS.md`) через **глобальный gitignore** (личный, на все репозитории) — тогда
репозиторный `.gitignore` не трогается:

```bash
git config --global core.excludesFile ~/.gitignore_global
printf '%s\n' 'ai-flow/' '.claude/' '.serena/' 'CLAUDE.md' 'AGENTS.md' 'BUILD_PROMPT.md' >> ~/.gitignore_global
```

Для одного репозитория без коммита правила — те же строки в `.git/info/exclude`. Помните: `.gitignore`
действует только на **неотслеживаемые** файлы; уже закоммиченное сначала уберите из индекса:
`git rm --cached <path>`.

## FAQ и решение проблем

**«No tasks in ai-flow/docs/tasks».** Нет ни одной фича-папки с задачами. Создайте доработку через
`/new-task` (или вручную по `PROMT_TASKS.md`). `README.md` внутри фича-папки задачей не считается.

**«ERROR: PyYAML is required».** Поставьте зависимость оркестратора: `pip install pyyaml`.

**Оркестратор не коммитит.** Проверьте, что вы в git-репозитории (`git status`) и что в `agents.yml`
`git.enabled` и `git.auto_commit` = `true`. Вне git-репо коммиты просто пропускаются — это нормально.

**«No tasks ready (unmet dependencies)».** У всех оставшихся задач есть незакрытые `Depends on:`.
Проверьте, что имена в `Depends on:` совпадают (по подстроке) с именами файлов задач, от которых зависите,
и что те уже в `done/`.

**Агент «завис» / тайм-аут.** Увеличьте `task_timeout` в `agents.yml` или разбейте задачу на более мелкие.
Слишком крупная задача — частая причина; целевой размер — 100–500 строк нового кода.

**Задача помечена выполненной, но код неверный.** Оркестратор считает успехом маркер завершения **или**
выход с кодом 0. Уточните `Acceptance Criteria` в задаче — именно они служат агенту определением готовности.
Файл задачи можно вернуть из `done/` обратно в фича-папку и перезапустить.

**Хук `memory-sync` ругается на рассинхрон.** Либо создайте недостающую память (`write_memory` / `/sync-docs`),
либо уберите лишнюю строку из таблицы `CLAUDE.md`, либо добавьте запись в `ignore_memories`.

**Использую не Claude Code.** Скиллы `/new-prd`, `/new-task`, `/sync-docs`, `/run-tasks`, субагенты и
хук — это механика Claude Code. Один раз прогоните `ai-flow/docs/prompts/PROMT_TOOL.md` из-под своего
CLI — он создаст те же точки входа в его формате и добавит его в `agents.yml` как исполнителя (см.
[раздел](#другой-инструмент-не-claude-code)). До адаптации скармливайте агенту промты напрямую:
`PROMT_PRD.md`, `PROMT_TASKS.md`, `PROMT_SERENA.md`.
