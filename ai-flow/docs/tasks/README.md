# Задачи (по фичам)

Задачи группируются по доработкам (фича или фикс — не важно). Одна папка = одна доработка:

```
ai-flow/docs/tasks/
├── MILESTONES.md                       # ключевые этапы реализации (план над фичами)
├── YYYYMMddHHmm_FEATURE_NAME/          # FEATURE_NAME — kebab-case название доработки
│   ├── README.md                       # DesignReview доработки (шаблон ниже)
│   ├── YYYYMMddHHmm_TASK_SUMMARY.md     # задача; TASK_SUMMARY — ≤5 англ. слов через "-"
│   ├── NOTES.md                         # заметки фичи: каждая задача дописывает, что построила
│   └── done/                            # сюда run_tasks.py ПЕРЕМЕЩАЕТ выполненные задачи
└── done/                               # глобальный каталог: сюда run_tasks.py ПЕРЕМЕЩАЕТ
    └── YYYYMMddHHmm_FEATURE_NAME/       # ПОЛНОСТЬЮ выполненные фичи (все задачи в done/)
```

- `done/` в корне `tasks/` — архив завершённых доработок, а не папка фичи: как только все задачи
  доработки уехали в её `done/` и проход проверки фичи зелёный (см. «Единица работы» ниже),
  `run_tasks.py` ПЕРЕМЕЩАЕТ всю папку доработки в `tasks/done/`.
  Дискавери задач эту папку игнорирует; зависимости на задачи из архивных фич по-прежнему видны.

- `MILESTONES.md` — ключевые этапы реализации PRD: цель этапа, покрытые требования/спеки, входящие
  фичи, критерии завершения, статус и контрольная задача. Планирование живёт здесь, а не в папках
  фич: папка выполненной фичи уезжает в архив, а план должен остаться. Формат и правила —
  `../prompts/PROMT_TASKS.md` §11.
- `YYYYMMddHHmm` — таймстамп (получить: `date +%Y%m%d%H%M`).
- Задачи выполняются в порядке имён (таймстамп → хронология); строка `Depends on:` уточняет порядок.
- `README.md` и `NOTES.md` внутри папки фичи задачами НЕ считаются. `NOTES.md` заранее не создают —
  его ведут агенты-исполнители.
- Создавать доработки: скилл `/new-task` (субагент `task-author`) или `../prompts/PROMT_TASKS.md`.
- После выполнения доработки её функциональность документируется в `../specs/<feature>/`
  (`README.md` — целевой, `IMPLEMENTED.md` — как реализовано) — автоматически, проходом проверки фичи.

## Ключевые этапы и контрольная сверка

PRD не режется в задачи целиком за один раз. Сначала он делится на **ключевые этапы** — срезы,
каждый из которых даёт проверяемую возможность («фундамент бэкенда запускается и покрыт тестами»,
«организатор публикует папку, и она видна в публичном каталоге»), — и этапы записываются в
`MILESTONES.md`.

Последняя задача последней фичи каждого этапа — **контрольная задача** сверки
(`<таймстамп>_revalidate-prd-and-plan-next.md`). Она не меняет продуктовый код и обязана:

1. сверить PRD с фактической реализацией по затронутым разделам;
2. сверить спеки (`../specs/NN-*.md`) — таблицы, сигнатуры, лимиты, коды ошибок, схему;
3. исправить разошедшееся в том же изменении, закрыть отвеченные открытые вопросы и завести новые;
4. зафиксировать as-built в `../specs/<feature>/IMPLEMENTED.md`, обновить памяти и changelog;
5. обновить `MILESTONES.md`: этап — `done`, следующий этап — уточнить состав фич;
6. нарезать задачи следующего этапа уже по исправленным PRD и спекам.

Смысл: нарезка задач читает текст спек. Если после этапа спеки описывают несуществующий контур или
другую версию платформы, ошибку унаследует каждая следующая задача, и агент-исполнитель реализует её
буквально. Одна контрольная задача на этап дешевле переделки десятка.

## Запуск

```bash
python ai-flow/run_tasks.py                    # все доработки
python ai-flow/run_tasks.py --feature user-login   # только совпадающие папки фич
python ai-flow/run_tasks.py --task add-login       # только задачи по имени
python ai-flow/run_tasks.py --max-parallel 4       # явные parallel batch до 4 воркеров (0/1 — выкл.)
python ai-flow/run_tasks.py --dry-run
```

## Параллельные задачи (явные batch-и)

По умолчанию задачи идут последовательно. Независимые задачи **одной** фичи можно объявить
параллельными строкой `Parallel with:` — взаимно и полностью: для группы `{A, B, C}` в A пишут
`B, C`, в B — `A, C`, в C — `A, B`. Оркестратор запускает группу одним атомарным batch-ем, только
когда все её участники готовы (`Depends on:` остаётся жёстким гейтом):

1. каждый воркер работает в отдельном detached git worktree от общего коммита и **не трогает общие
   доки** — файл правил, журнал, спеки, памяти, Markdown задач (включая `NOTES.md`); свою запись для
   заметок фичи он печатает в итоговом отчёте;
2. успешные коммиты воркеров переносятся cherry-pick-ом в порядке имён задач в интеграционный
   worktree, где один проход интеграции сводит их, пишет записи в `NOTES.md` и собирает решение (при
   `unit_of_work: task` — ещё тесты и доки);
3. только после этого основная ветка перематывается fast-forward. Любой сбой (воркер упал, тронул
   общий файл, коммиты конфликтуют) оставляет основное дерево нетронутым; готовый, но не влитый batch
   сохраняется в ветке `ai-flow/recover-<задача>`.

Требования: git с `auto_commit`, чистое рабочее дерево; группа целиком помещается в
`parallel.max_workers` (по умолчанию 2) и не дробится. Односторонняя, межфичевая или частично готовая
группа — ошибка, прогон останавливается. `--task` всегда последователен. Когда независимость
сомнительна (общие файлы, миграции, конфиг, контракт «производитель → потребитель»), параллельность
не объявляют — связь выражают через `Depends on:`. Правила нарезки — `../prompts/PROMT_TASKS.md` §3, §10.

## Единица работы: тесты и документация — то, что запросили

Гейт «тесты зелёные» и документация привязаны к той единице работы, которую запросили
(`unit_of_work` в `../../agents.yml`, по умолчанию `feature`):

- **Запрошена фича** (запуск без `--task`, или «реализуй фичу X» в сессии). Каждая задача пишет свои
  тесты по TDD (из `## Test Cases`) и обязана оставить решение **компилирующимся**, но тесты не
  запускает. Из документации задача ведёт только `NOTES.md` фичи: что построено, файлы, API для
  следующих задач, решения, паттерны и доменные правила, конфликты. Следующие задачи получают эти
  заметки в промпте и не исследуют код заново. После последней задачи оркестратор сам запускает
  **проход проверки фичи** (`../prompts/PROMT_VERIFY.md`): сборка, весь набор тестов, исправления до
  зелёного, затем один раз по заметкам — журнал, спека, `IMPLEMENTED.md`, индекс спек, памяти. Только
  зелёный проход переносит фичу в `tasks/done/` отдельным коммитом. Упавший проход оставляет фичу
  активной (все задачи в её `done/`), и следующий запуск по фиче повторяет проверку.
- **Запрошена одна задача** (`--task`). Задача сама прогоняет тесты и обновляет документацию. Если она
  закрыла фичу, после неё всё равно идёт проход проверки фичи.

Отдельные задачи «прогнать тесты» или «обновить доки» в конце фичи не создавайте — это делает проход
проверки.

## Шаблон `README.md` доработки (DesignReview)

Беглый обзор доработки: суть, ценность, архитектура.

```markdown
# <Feature Name>

- Type: feature | fix
- Created: YYYY-MM-DD HH:MM
- Status: planned | in-progress | done

## Summary
<глобальная суть: что и зачем, 2–4 предложения>

## Value
<ценность: пользовательская / бизнес / системная>

## Architecture
<затрагиваемые компоненты, подход, поток данных, ключевые решения>

## Scope
- In scope: <что входит>
- Out of scope: <что не входит>

## Tasks
- [ ] YYYYMMddHHmm_task-summary — <одна строка>

## Acceptance
<как поймём, что доработка готова; обязательно: после КАЖДОЙ задачи решение собирается/компилируется,
после всей фичи — собирается и весь набор тестов проходит (проверяет проход проверки фичи)>
```

Каждая задача — законченный срез: сама по себе собирается, и тесты прошли бы после неё (даже если в
прогоне фичи их запустит только проход проверки). Если задача меняет тип,
сигнатуру, интерфейс, enum, DTO или контракт — та же задача правит всех его потребителей (никаких
«поменяли тип в одной задаче, чиним использования в другой» — промежуточный коммит не скомпилируется).
Порядок задач не должен вести через несобирающееся состояние; собранная фича билдится целиком.

## Шаблон файла задачи

Структурные заголовки (`# <Title>`, `## Changes`, `Depends on:`) обязательны — по ним работает парсер
(первый `#`-заголовок = название; `Depends on:` / `Зависит от:` = зависимости; `Parallel with:` /
`Параллельно с:` = параллельные пиры; ссылка на другую задачу — по её имени/подстроке или `none`).
Все ссылки держите в самой строке `Depends on:` (длинный список можно перенести строкой с отступом,
но не новым пунктом списка — хвост потеряется молча). Пояснения в скобках, бэктики, суффикс `.md` и
текст после тире парсер игнорирует; ссылка обязана содержать `_` или `-`.

```markdown
# <Task title>

## Overview
<что и зачем>

## Context
- Templates: <шаблон §N «заголовок» — только нужные разделы>
- Memories: <имена памятей для read_memory>
- Specs: <файл спеки § раздел>
- Code: <3–7 файлов/символов: образец, что расширить, где регистрировать — с причиной>

## Changes
### 1. <действие>
**File**: `path/to/file.ext`
<сигнатуры / структуры / схемы>

## Dependencies
- Depends on: <имя другой задачи в этой папке | none>
- Parallel with: <все взаимно объявленные пиры в этой папке | none>

## Test Cases
**Test file**: `path/to/tests/<subject>_test.ext`
**Mocks**: <каждая внешняя зависимость и что возвращает её заглушка>

| # | Case | Arrange | Act | Assert |
|---|------|---------|-----|--------|
| 1 | <hot path> | <конкретные значения> | <вызов> | <конкретный результат> |
| 2 | <корнер-кейс> | ... | ... | ... |

## Acceptance Criteria
1. [ ] <проверяемый критерий>
2. [ ] Решение целиком собирается/компилируется и тесты проходят штатным тулингом проекта
       (`read_memory("build-and-verify")`) — всегда последний критерий каждой задачи. Сборку
       проверяет задача; тесты — сама задача при запуске `--task`, или проход проверки фичи.
```

Секция `## Context` обязательна — это список чтения для исполнителя. Автор задач уже изучил код при
нарезке и записывает, какие разделы шаблонов, памяти и якоря в коде нужны именно этой задаче, чтобы
исполнитель не грузил шаблоны целиком и не искал по всему коду заново. Подробности —
`../prompts/PROMT_TASKS.md` §6a.

Секция `## Test Cases` обязательна и пишется **до** реализации. Только unit-тесты: все внешние
зависимости (БД, HTTP, брокер, ФС, время, random) мокируются; сценарии с реальной инфраструктурой —
это отдельная интеграционная задача. Минимум покрытия: hot-paths + корнер-кейсы (границы, пустые
значения, невалидный ввод, ошибки моков). Подробности и правила — в `../prompts/PROMT_TASKS.md` §6.
